# 「寫出好 Skill」

幫使用者把一段真實工作，做成第一版能用的 Skill。

Skill 的價值是讓 AI 每次都走一套可預期的判斷過程，不是讓每次答案一模一樣。模型本來就知道的常識、已經做得好的行為，不要再寫一次；把空間留給它不知道、容易漏掉或只屬於使用者的判斷。

預設保持輕量：先做一個 `SKILL.md`。只有工作真的需要長參考資料時才加 `references/`；只有固定、容易出錯而且會重複執行的操作，才加 `scripts/`。

這是一個初版框架。使用者跑過幾次後，應該根據自己的習慣、例外與驗收標準修改，而不是永遠照抄本 Skill。

## 平台與安裝位置

本 Skill 可在 Claude Code、Codex 或其他能讀取 Markdown Skill 的 AI Agent 使用。

先沿用 Pro-kit 01 記錄的：

```text
SKILLS_DIR=[AGENT_HOME]/000_Agent/skills
```

新 Skill 一律寫進 `[SKILLS_DIR]/<skill-name>/`。`000_Agent/skills/` 是唯一原始資料夾；Claude Code 與 Codex 的全域或專案入口只是指向它的捷徑連結。

若找不到這個設定，先告訴使用者並建議跑 Pro-kit 01。使用者明確要求繼續時，依 Pro-kit 01 B-5 安全建立唯一原始資料夾與全域入口（Claude Code `~/.claude/skills`、Codex `~/.agents/skills`）。不得自行另建一份平行原始資料，也不要把同一批個人 Skills 再掛一份到專案層。

## Step 0：Codex 規劃模式防呆

如果目前是 Codex：

- 尚未完成必要訪談，而且目前不是規劃模式：先教使用者點輸入框左下角 `＋` →「規劃模式」，然後停止。
- 目前是規劃模式：一次問一題，每題只放 2～3 個互斥選項；只能訪談、整理 brief 與計畫，不得寫檔。
- brief 已確認：請使用者切回一般模式，再做 baseline、建立或修改 Skill、跑測試。

如果使用者已帶著確認好的 brief，而且目前是一般模式，不要叫他重跑訪談，直接從 baseline 開始。

## Step 1：先問一題，選擇情境

如果環境有互動式提問工具，就用單選選單。每題只放 2～3 個互斥選項；沒有時，用純文字列出同樣選項。

先問：

```text
你想把哪一類做法留下來？

1. 我自己的做法
2. 別人或團隊的做法
3. 我不確定，先描述問題
```

選「別人或團隊的做法」時，再問：

```text
資料主要來自哪裡？

1. 身邊高手：同事、主管或前輩
2. 團隊 SOP：正在執行的共同流程
3. 公開專家：合法取得的公開資料
```

使用者若已說明情境，不要重問，直接確認你判斷的路線。若他要建立的是長期個人寫作風格，優先轉交 `personal-style-loop`；其他工作方法才繼續本 Skill。

## Step 2：最多四個必要追問

整段建立流程最多追問四個必要問題，不要一次丟長問卷。已經從對話或檔案得到的資訊，不要再問。

優先收斂：

1. **真實工作**：你希望它反覆幫你完成哪一類工作？
2. **成果與驗收**：完成後要交付什麼？你怎麼判斷做得好？
3. **參考資料**：目前有哪些作品、文件、案例、訪談或公開來源？
4. **邊界**：什麼情況不能做、資料不足要問誰、有哪些敏感內容？

若使用者選「我不確定」，先讓他描述最近一次卡住的工作，再判斷最接近哪條路。能直接做一次性任務就直接做，不要為了產出 Skill 而硬做 Skill。

## Step 3：依情境收集參考資料

先明確請使用者提供素材：請他貼上內容、給檔案路徑，或指出公開來源。只知道「有哪些資料」還不夠；拿到素材之前，不要進入萃取，也不要展開長串訪談。

### 路線 A：自己

使用：

- 2～3 份有代表性的真實成品。
- 使用者曾經給過的修改或回饋。
- 1 份先保留、不放進建立階段的成品。

萃取的是選擇、判斷、順序與品質標準，不只整理語氣形容詞。

### 路線 B：身邊高手

使用：

- 對方同意提供的訪談或工作說明。
- 成功案例與失敗案例。
- SOP、檢查表或經過匿名化的對話紀錄。

先確認同意、權限與機密邊界。最後安排原本的高手 review，確認 AI 沒有把他的判斷寫歪。

### 路線 C：團隊 SOP

使用：

- 口述、舊文件、截圖、執行紀錄。
- 新人常問的問題。
- 既有 SOP 與相關上下游文件。

先查是否已有同名或衝突版本。把例外、判斷規則與停止條件寫進去，不只列第一步、第二步。

### 路線 D：公開專家

先縮小成一個工作領域，例如「產品取捨」或「溫和但堅定地拒絕」，不要直接做包山包海的完整人格。

來源原則：

- 至少使用兩種不同場景的公開來源，優先本人長文、公開演講、訪談、決策或作品案例。
- 加入矛盾、限制或批評資料，避免只收正面內容。
- 記錄來源與調研截止時間。
- Skill 保存轉化後的摘要、規則與來源索引，不重新打包大量原始內容。

誠實邊界：

- 不聲稱本人授權、合作或背書，除非有明確證據。
- 不假扮本人，不把推測寫成直接引言。
- 專家沒談過的問題，要標註「以下是根據公開框架的推論」。
- 醫療、法律、投資等高風險領域保留專業覆核。

## Step 4：先跑沒有 Skill 的 baseline

建立 Skill 前，先拿一個真實任務讓目前的 AI 做一次。

記錄：

- 哪裡做對。
- 哪裡太通用、判斷錯誤、漏掉邊界或輸出不合用。
- 使用者真正想改的是哪一點。

baseline 已經做得好的地方，不要寫成新規則。只補模型不知道、容易漏掉或使用者有明確偏好的內容。

### 寫入前先做精煉測試

每一條候選內容都問：拿掉它，AI 的行為會變差嗎？

- 不會：刪掉。這通常是模型已經知道的常識或沒有改變行為的提醒。
- 會，而且每次都要用：留在 `SKILL.md`。
- 只在某一條分支需要：移到對應段落，或放進有清楚讀取時機的 `references/`。
- 已在其他文件有唯一正本：只留下何時要讀的指向，不要複製一份。

同一個意思只保留一個位置。新增規則前先搜尋既有內容；改進以刪除重複、過期與 no-op 為優先。

## Step 5：建立最小可用 Skill

先檢查目標資料夾有沒有同名 Skill。已存在時先讀取並向使用者說明是更新或另建，不要直接覆蓋。

預設只建立：

```text
<skill-name>/
└── SKILL.md
```

`SKILL.md` 至少包含：

```markdown
---
name: <kebab-case-name>
version: 0.1.0
description: >-
  這個 Skill 解決什麼問題、什麼時候使用，以及哪個近似情境不該觸發。
user-invocable: true
last-updated: YYYY-MM-DD
---

# <Skill 名稱>

## 使用時機

## 不適用情境

## 必要輸入

## 判斷與工作流程

## 輸出格式

## 停止條件

## 驗收標準
```

寫作原則：

- description 同時寫「應觸發」與「不應觸發」。
- 只放 AI 不知道的規則、例外與參考方式。
- 能讓模型自行判斷的地方，不要堆限制。
- 使用繁體中文；技術名詞保留英文。
- 先解釋原因，再給必要規則。

只有符合以下條件才新增資料夾：

- `references/`：每次工作都要回查、而且放進 `SKILL.md` 會太長的參考資料。
- `scripts/`：固定、容易出錯、重複執行，而且用程式比自然語言可靠的步驟。

## Step 6：共用 Harness／Loop

所有分支都要跑兩種測試：

1. **校準題**：使用已知結果的案例，確認 Skill 能重現關鍵判斷。
2. **保留／未知／邊界題**：依情境選一題，確認 Skill 不是背答案。

| 情境 | 第二題怎麼選 |
| :-- | :-- |
| 自己 | 使用建立階段沒看過的保留作品 |
| 身邊高手 | 邊界案例或資料不足案例，再請本人 review |
| 團隊 SOP | 例外情境或讓新人試跑 |
| 公開專家 | 專家沒直接談過的未知題，或爭議邊界題 |

比較 baseline 與使用 Skill 的結果。若沒有變好：

1. 找出一個最明確的落差。
2. 只補能解決這個落差的規則或參考資料。
3. 用同一題再測一次。

不要為了看起來完整，一次加入整套新框架。

## Step 7：落地驗證與個人化

宣稱完成前，實際確認：

- 新 Skill 的 `SKILL.md` 已寫入。
- 名稱與資料夾一致。
- 校準題已執行。
- 第二題已執行。
- 測試造成的修改已寫回 Skill。
- 安裝位置確實位於 `SKILLS_DIR`，而不是另一份平行資料夾。
- 使用者已從所選 scope 開啟全新對話，真正用 `/skill-name`（Claude Code）或 `$skill-name`（Codex）呼叫成功。

最後回報：

```markdown
## 已完成

- Skill 名稱：
- 安裝位置：
- 它會處理：
- 不會處理：
- 使用的參考資料：
- baseline 的主要問題：
- 測試後補上的規則：
- 下一輪個人化建議：
- 全新對話呼叫驗證：
```

提醒使用者：這是 `0.1.0` 初版。未來每次遇到真實失敗，只修一個最重要的落差。等真的需要，再新增 references、scripts 或更嚴格的測試。

## 課程版刻意沒有什麼

為了讓第一次建立 Skill 保持順手，本版不包含：

- 六個並行研究 Agent。
- Atlas 或 Drift 自動體檢。
- 每題跑三次的 20 題 eval。
- 四種成熟度治理。
- GitHub 打包與跨平台發布流程。
- 預設 subagent 審查。

這些功能不是永遠不能用。等 Skill 已經成為日常工具、多人共用或碰到高風險工作，再選擇性升級。
