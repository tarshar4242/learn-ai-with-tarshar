先看全貌為什麼會有這麼多種「儲存」？

為什麼要先看全貌？ 以前資料很單純：一台電腦、一個資料庫、整齊的表格。後來資料變多、變雜、要求變快，舊做法一個一個卡住，於是每卡住一次，就長出一種新的儲存方式。每一種儲存或資料庫，都是為了解決某一種特定問題而生。記住「它解決什麼問題」，名詞就不會混在一起。

新狀況舊做法卡在哪於是出現
資料量遠超過一台伺服器一台機器裝不下分散式儲存：很多台機器一起存（HDFS、雲端物件儲存）
資料不整齊：圖片、影片、文字、JSON表格欄位規定死，放不進去NoSQL、資料湖
要超快查：購物車、快取傳統資料庫太慢鍵值儲存、記憶體資料庫（Redis）
要查「誰跟誰有關」表格查關係要連好幾層圖形資料庫（Neo4j）
要做大量分析、報表處理交易的資料庫不適合資料倉儲、欄式儲存
怕資料遺失只有一份，一壞就沒了複製、備份、糾刪碼

單元 ①三種儲存：區塊、檔案、物件

為什麼需要這個概念？ 「區塊」「檔案」「物件」這三個詞常常一起出現，又都叫「儲存」，很容易糊成一團。它們的差別在於：資料被切成什麼單位、用什麼方式找回來。雲端服務（像 AWS、Azure）會把這三種分別做成不同產品，所以看到產品名要能配回類型。

一步步搭起來

  1. 區塊儲存：把硬碟切成一格一格固定大小的空櫃子，格子裡放什麼、怎麼排，由作業系統或資料庫自己安排。最貼近硬體，所以最快。
  2. 檔案儲存：在格子上面加一層「檔案系統」，用資料夾和檔名（路徑）來找資料，大家習慣的共用資料夾就是這種。
  3. 物件儲存：不用資料夾，每份資料打包成一個「物件」＝資料本身＋標籤（中繼資料）＋唯一 ID，丟進一個大桶子，用網址 API 存取。量再大都能往上加，而且便宜。
區塊 Block檔案 File物件 Object
比喻一格格空櫃子有資料夾的檔案櫃貼好標籤的貨架
怎麼找資料作業系統／資料庫自己管理格子路徑＋檔名網址 API＋物件 ID
代表SAN、AWS EBSNAS、NFSAWS S3、Azure Blob
適合資料庫、虛擬機（要快）共用資料夾、辦公文件圖片影片、備份、資料湖（量大、便宜）
  • NAS 與 SAN：NAS 提供檔案級儲存，像一個共用資料夾；SAN 提供區塊級儲存，像直接幫伺服器接上一顆硬碟。
  • 資料湖的底層通常是便宜、可以一直擴充的物件儲存或 HDFS。
易錯提醒：S3、Azure Blob 是物件儲存，不是區塊儲存。判斷口訣：看到「網址存取、標籤、桶子（bucket）、量大便宜」→ 物件；看到「像一顆硬碟、給資料庫或虛擬機用」→ 區塊；看到「資料夾、路徑、共用」→ 檔案。另外，這裡的「區塊儲存」跟下面 HDFS 把檔案「切成區塊」是不同層次的事，別混在一起。

單元 ②NoSQL 的四種資料模型：鍵值、文件、寬欄、圖形

為什麼需要這個概念？ 傳統關聯式資料庫（SQL）把資料放進欄位事先規定好的表格，很嚴謹，也保證強一致（ACID）。但遇到「資料結構常變」「資料量超級大」「關係超複雜」就吃力。NoSQL（Not Only SQL）不是一種資料庫，而是一整個家族，每一種擅長一件不同的事。這一塊最常考的就是「產品名 ↔ 類型」配對。

一步步搭起來

  1. 先記住共同點：NoSQL 大多容易水平擴充（高擴展性）、結構有彈性（彈性綱要）、高可用性。共同的代價是不一定提供傳統資料庫那種強 ACID 交易保證。
  2. 再用同一件事比較四種存法：下圖把「小美買了咖啡」這件事，分別存進四種模型。
  3. 鍵值：拿一個「鍵」直接查出「值」，像查字典，最簡單也最快。
  4. 文件：每筆資料是一份類似 JSON 的文件，每份文件的欄位可以不一樣。
  5. 寬欄：看起來像大表格，用「列鍵」找到一行，但欄位可以隨時增加、空的不佔空間，資料分散在很多台機器。
  6. 圖形：只存「點」（人、物）和「線」（關係），專門回答「誰跟誰有關」。
類型一句話代表產品適合
鍵值 Key-Value拿「鍵」直接查出「值」，像字典Redis快取、購物車、計數器（要超快）
文件 Document一份份 JSON 文件，欄位可不同MongoDB資料結構常變動、商品型錄、內容管理
寬欄 Wide-Column大表格，但欄位自由增減，分散在多台機器Cassandra、HBase海量寫入、時間序列、感測器資料
圖形 Graph點（人、物）＋線（關係）Neo4j社群關係、推薦系統、詐欺偵測

用情境關鍵字反推類型

  • 看到「快取」「超低延遲」「購物車」「計數器」→ 鍵值（常放在記憶體裡）。
  • 看到「JSON」「結構常變」「每筆欄位不同」→ 文件。
  • 看到「海量寫入」「時間序列」「感測器」→ 寬欄。
  • 看到「關係複雜」「社交網路」「推薦」「誰認識誰」→ 圖形。
  • 產品配對口訣：瑞迪斯查字典、蒙果看文件、卡珊卓拉存大表、奈歐四傑畫關係。
易錯提醒：「寬欄」（Wide-Column，Cassandra、HBase）是 NoSQL 的一類；「欄式」（Columnar，Parquet、ORC 這類為分析查詢設計的存法）是另一個概念，在單元 ④。名字都有「欄」，用途不同。另外 Redis 是鍵值，不是欄式；MongoDB 是文件，不是鍵值。

單元 ③HDFS：把大檔案切碎、每塊各存 3 份

為什麼需要這個概念？ HDFS（Hadoop 分散式檔案系統）是大數據的「儲存底座」。一個檔案大到一台機器裝不下、讀不完，怎麼辦？切成大塊，分散到很多台便宜的機器上，而且每塊多存幾份，壞掉幾台也不怕。

一步步搭起來

  1. 切成區塊（Block）：預設 128 MB 一塊（舊版 64 MB，也可以設 256 MB），比一般電腦檔案系統的區塊大很多。
  2. 每塊存 3 份：預設複製係數是 3，三份放在不同機器。壞掉一兩台，資料還在，這就是容錯。
  3. NameNode＝總機／目錄：只記「檔案叫什麼、每個區塊放在哪幾台」（命名空間＋區塊對應表），不存實際資料。
  4. DataNode＝倉庫：真正存放區塊的機器。
角色屬於誰負責什麼
NameNodeHDFS命名空間、區塊對應表（目錄），不存資料本身
DataNodeHDFS存放實際的區塊
ResourceManagerYARN整個叢集的運算資源分配
NodeManagerYARN每台機器上的運算資源管理
HDFS 擅長HDFS 不擅長
高吞吐量：一次順序讀寫大量資料極低延遲的隨機讀寫（這種需求改用 Redis 等）
可靠地存非常大的檔案、串流式存取大量小檔案（NameNode 的目錄會被塞爆）
高擴展性、高容錯性完整支援 POSIX 的所有檔案操作
易錯提醒：存「目錄」的是 NameNode，不是 DataNode；ResourceManager、NodeManager 是 YARN 管運算資源的角色，跟 HDFS 存資料無關。分散式檔案系統的優點是高擴展、高容錯、高吞吐，「極低延遲」不是它的優點。要挑出「不是優點」的那一個時，把每個說法逐一換成「這是它的優點嗎？」再檢查一次。

單元 ④欄式儲存、資料倉儲與資料湖

為什麼需要這個概念？ 同一份資料，要「記一筆訂單」跟要「分析全部訂單」，最適合的存法不一樣。前者一次要一整筆，後者一次只要某一欄的所有值。分析需求長大之後，又分化出資料倉儲、資料湖、湖倉一體這幾種「大型資料存放區」。

一步步搭起來：列式 vs 欄式

  1. 列式：一整列一整列存，讀「整筆訂單」很快，適合交易處理（OLTP）。
  2. 欄式：一整欄一整欄存，要算「平均價格」只讀價格那一欄，快很多；同一欄資料型態一樣，還很好壓縮，適合分析處理（OLAP）。
  3. Parquet、ORC 是資料湖裡最常用的欄式檔案格式。

資料倉儲、資料湖、湖倉一體

資料倉儲 DW資料湖 Data Lake湖倉一體 Lakehouse
存什麼整理過的結構化資料各種原始資料（結構化、半結構化、非結構化）兩者兼具
綱要何時定寫入時先定（Schema-on-Write）讀取時才定（Schema-on-Read）兩者兼具
用途BI、報表、決策分析（OLAP）探索、機器學習、保存原始資料同一份資料兩種用途都能做
底層關聯式資料庫、欄式儲存物件儲存或 HDFS（便宜、可擴充）在資料湖上加管理與 ACID（例：Delta Lake）
  • 資料沼澤（Data Swamp）：資料湖沒有治理，什麼都往裡丟，最後品質低、找不到、不能用。
  • 資料市集（Data Mart，也有人譯作資料超市）：資料倉儲的子集，只聚焦某個部門或某個主題。

維度緩慢變更 SCD：客戶搬家了，倉儲怎麼記？

客戶小美本來住台北，後來搬到高雄。資料倉儲裡的「客戶」維度要怎麼改，有三種經典做法：

類型做法結果保留歷史嗎
Type 1直接覆蓋舊值只剩「高雄」沒有
Type 2新增一列，用生效日、失效日或版本號區分「台北（到 8/1）」與「高雄（8/1 起）」兩列都在有，完整保留
Type 3新增一個欄位存上一個值目前城市＝高雄，先前城市＝台北只保留上一次
易錯提醒：ORC 的全名是 Optimized Row Columnar，名字裡有 Row，但它是欄式格式，不要被名字騙。SCD 的記法：Type 1 覆蓋、Type 2 加一列、Type 3 加一欄；要「完整歷史」就是 Type 2。

單元 ⑤CAP 定理與資料保護

為什麼需要這個概念？ 資料一旦分散在很多台機器，就會遇到兩個現實問題：機器之間的網路會斷，以及機器本身會壞。CAP 定理說明網路斷掉時系統只能怎麼取捨；複製、糾刪碼、備份則是防止機器壞掉時資料消失。

一步步搭起來：CAP 定理

  1. C 一致性（Consistency）：每個人讀到的都是最新資料。
  2. A 可用性（Availability）：每個請求都會得到回應。
  3. P 分區容錯性（Partition Tolerance）：網路斷成兩半，系統仍能繼續運作。
  4. 結論：三者無法同時被完全滿足。分散式系統的網路一定可能斷，P 必須要，所以斷線時只能在 C 和 A 之間二選一（CP 或 AP）。

資料保護：複製、糾刪碼、3-2-1、RPO 與 RTO

複製 Replication（例：HDFS 存 3 份）糾刪碼 Erasure Coding
做法整份資料多存幾份資料切成 k 塊，再算出 m 塊「校驗塊」，壞掉任意 m 塊都能算回來
空間用量3 份＝佔 3 倍空間例如 6 塊資料＋3 塊校驗＝只佔 1.5 倍空間
容錯3 份可壞 2 份6＋3 可壞任意 3 塊
代價簡單、讀取快計算較複雜，修復時要重算；資料仍分散在網路上的多台機器
名詞意思記法
3-2-1 原則3 份資料、2 種不同媒介、1 份放異地防同一地點的火災、水災、被盜讓所有副本一起消失
RPO最多能容忍遺失多久的資料Point＝資料回到哪個時間點；RPO 1 小時 → 至少每小時備份一次
RTO最多能容忍停機多久Time＝花多久恢復
易錯提醒：CAP 的 C 是 Consistency 一致性，不是 Capacity（容量）也不是 Cost（成本）；A 是 Availability，不是 Authenticity。糾刪碼的優勢是儲存效率高、更省空間，代價是計算比較複雜，不是「比較簡單」。

總整理本章要記的十五句話

  1. 每種儲存都是為了解決一個特定問題；先問「要解決什麼問題」，再配名詞。
  2. 區塊＝格子（資料庫、虛擬機）；檔案＝資料夾與檔名（NAS）；物件＝貼標籤的貨架（S3、Azure Blob）。
  3. NAS 是檔案級、SAN 是區塊級；資料湖底層常用物件儲存或 HDFS。
  4. Redis＝鍵值：像字典，用在快取。
  5. MongoDB＝文件：一份份 JSON，結構常變也沒關係。
  6. Cassandra、HBase＝寬欄：海量寫入、時間序列。
  7. Neo4j＝圖形：點與線，查「誰跟誰有關」。
  8. NoSQL 的長處是高擴展、彈性綱要、高可用；強 ACID 交易保證不是它的長處。
  9. HDFS 切 128 MB 大區塊、每塊存 3 份；NameNode 管目錄、DataNode 存資料；重吞吐，不重低延遲。
  10. ResourceManager、NodeManager 屬於 YARN，管運算資源，不是 HDFS 的儲存節點。
  11. Parquet、ORC 是欄式；分析（OLAP）用欄式，交易（OLTP）用列式。
  12. 資料倉儲寫入時定綱要、資料湖讀取時定綱要；湖倉一體＝資料湖加上 ACID（Delta Lake）。
  13. SCD：Type 1 覆蓋、Type 2 新增一列保留完整歷史、Type 3 新增一欄。
  14. CAP＝一致性、可用性、分區容錯性，三者不能同時完美；C 不是 Capacity。
  15. 3-2-1＝3 份、2 種媒介、1 份異地；RPO 看可遺失多少資料、RTO 看多久恢復；糾刪碼比複製省空間。
