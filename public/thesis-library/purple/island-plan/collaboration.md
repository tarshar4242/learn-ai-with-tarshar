# 論文智能島：Claude 獨立評估

我沒有查網，也沒有跑任何效能測試，以下全是依你提供的背景做的判斷。

## 1. 島結構與手機首屏

**大方向同意你的 6 島，但有兩處不同意。**

- 方法工坊和 A/B 實驗室首版內容會很薄，建議合成「實驗島」，裡面放 A 字面查找、B 口語理解兩棟建物，方法說明當第三棟。這樣首版是 5 島，每座都有實質內容。
- 公開研讀庫不要當一座島混進來。它該是另一個視覺不同的「公開海岸」，旁邊標示「只放公開內容」。公私混在同一張地圖，是最容易出事的地方。

綠區用「港口入口」就好，不必當島。

**iPhone 首屏**只放三樣：一張「現在狀態」卡（第三章 3.1–3.3 進度、下一步、最後更新時間）、5 座可點的大島、一顆「問論文」按鈕連到紫區平台。點島後從下方彈出 bottom sheet，顯示狀態、來源、下一步。

首版建議用 2D 等距插圖，延伸既有的 /architecture，不要上 12 島、50 棟的 Three.js。手機效能和載入我沒測過，所以只能說風險高，不能說一定卡。

## 2. 三層與真實界線

| 層 | 內容 | 規則 |
|---|---|---|
| 展示 | 日夜、雲、小人走路 | 純裝飾，不帶資訊 |
| 研究管理 | 章節進度、文獻清單、會議待辦 | 來自 vault 快照，必附來源路徑、時間、commit |
| AI 執行 | A/B 查詢、評分、引用 | 來自實際執行紀錄，附 run 編號 |

**界線只有一條：沒有來源的動態，一律標「示意」。** 小人搬資料、Codex 與 Claude 的協作線，只有綁到真實交班紀錄時才能當事件，否則會讓人以為系統正在做它沒做的事。快照過期要在畫面上顯示警示。

## 3. 模型分工與最小選型試驗

A 不需要模型。B 要拆成三塊分開評：本機 BGE 檢索、生成、引用核對。Codex 與 Claude 在這裡是開發和互審的夥伴，不是島上的執行元件。

**試驗設計：**
- 固定同一份語料、同一批檢索結果、同一份提示詞。
- 只換生成模型，候選 2 到 3 個，且必須先確認在她的帳號實際可用。
- 題目由她的正式題庫抽 15 到 20 題，盲評。
- 評分看引用是否正確、有無編造、查不到時會不會老實說、口語理解、實測延遲與實際 token 成本。
- 重跑 2 次看穩定度。

gpt-5.4-mini 維持「暫用基準」標籤。100 美元 API 額度的餘額沒查過，訂閱與 API 也是分開計費，兩者都不能拿來證明品質。

## 4. 照抄原提示詞的風險與必要 MVP

**風險：**
- 規模過大，手機可能吃不消。
- 外部 CDN 依賴。
- 假的日誌、假的搬運會被當成真事。
- 單一 HTML 若內嵌私人草稿，一旦公開部署就外洩。
- 美感先行，資料契約後補，最後變成好看但不可信。

**必要 MVP：**
1. 一份唯讀快照 JSON，欄位有狀態、來源、時間、下一步。
2. 5 座可點島加 bottom sheet。
3. 連到紫區平台與 /architecture。
4. 過期警示。
5. 不改引擎。

只放在內網（100.x 位址）。

## 5. 最需先決定的一件事

**快照的唯一真實來源，和公私邊界：由誰、從哪裡、多久寫一次這份快照，以及公開版永遠不讀紫區。**

正式題目語料與評分規程會卡住選型，但不卡島的首版。
